_Date: 2026-11-15 · Author: Backend Engineer · Status: **PROPOSAL, documentation only. Nothing here is approved for implementation.** No code, test, dependency, lockfile, `.env*`, migration or other document was changed to produce it. No database, no OCI endpoint and no credential was touched._

## 2. Target architecture

```
 browser (React)                        Express backend                                 OCI
 ---------------                        ---------------                                 ---
 POST /images/upload/:collectionId  --> authz (owner) -> multer (limits) -> validate     
                                        -> ObjectStorage.put()  -----------------------> private bucket
                                        -> INSERT Image (object_key, metadata)  -> PostgreSQL
 GET  /albums/summaries             --> owner-scoped SQL -> ReadAccess.createReadUrl()   (no OCI call in option C)
 <img src=url>  (backend URL, token) -> verify token -> owner-scoped SQL -> getStream() -> OCI GetObject
```

Components (all new files; proposal):

- `lib/storage/objectStorage.ts`: the **provider-neutral interface** used by routes and models:
  ```ts
  interface ObjectStorage {
    put(key: string, body: Buffer | Readable, meta: { contentType: string; contentLength: number; cacheControl?: string; contentDisposition?: string; sha256?: string }): Promise<{ etag?: string }>;
    delete(key: string): Promise<void>;            // idempotent: "not found" is success
    exists(key: string): Promise<boolean>;         // HeadObject
    getStream(key: string): Promise<{ stream: Readable; contentType?: string; contentLength?: number; etag?: string }>;
    createReadUrl?(key: string, ttlSeconds: number): Promise<{ url: string; expiresAt: Date }>;  // only the PAR adapter implements it (options A, B, D)
  }
  ```
  The existing `ImageUrlSigner` (`getReadUrl(objectKey, ttl) -> { url, expiresAt }`) is kept as the **read-access** boundary, because the route code already depends on it and the response contract (`url`, `expiresAt`) is provider-neutral. It becomes an implementation detail whether the `url` is an OCI PAR or a backend token URL.
- `lib/storage/ociObjectStorage.ts`: the OCI adapter (the only file importing `oci-*`). `lib/storage/memoryObjectStorage.ts`: an in-memory adapter (a `Map<string, {body, meta}>`) for tests and for local development without OCI (`STORAGE_DRIVER=memory`; refused when `NODE_ENV=production`). Contract tests run the same suite against both (section 13).
- `lib/imageToken.ts`: HMAC token for option C (section 4.3).
- `config/env.ts` gets a `storage` block (names in section 3.3); the OCI SDK is created once per process and injected through `createApp(config, verify, mountExtra, deps)` exactly like `urlSigner` today (`app.ts:20-35`), so route code and tests never import the SDK.
- Business code never calls the SDK: `imageRoute.ts` calls `storage.put/delete`, models never see the SDK.

### 3.4 What the infrastructure owner must provide (REQUIREMENTS, not actions for agents)

1. A **private** bucket (no public access type, no public read policy), plus its name, the tenancy **namespace**, and the **region**.

3. IAM policy for the backend identity, **least privilege, scoped to the one bucket**, with the verbs from Oracle's policy reference (VERIFIED today):

   | Application operation | OCI permission | Verb that includes it |
   |---|---|---|
   | `put` new object | `OBJECT_CREATE` | `manage objects` |

## 4. Temporary access URLs: options, numbers, recommendation

### 4.1 Facts that drive the analysis

- OCI Object Storage has no S3-style presigned URL. Its mechanism is the **Pre-Authenticated Request (PAR)**: created with an API call (`CreatePreauthenticatedRequest`), it is a **bucket resource** with an id, listed and deleted via API, valid until its `timeExpires` or until deleted (VERIFIED, Oracle docs fetched today). Docs: expiry is required and unbounded, no per-bucket count limit is stated ("unlimited"), a PAR cannot be edited, the URL "gives anyone who has the URL access", and the PAR's creator permissions are checked on each use (so the creating principal must keep its permissions).
- Creating a PAR requires `PAR_MANAGE` = `manage buckets` (broad, see 3.4).
- Object Storage request-rate **service-level objective** per tenancy (VERIFIED): read 12,000 RPS (3-AD regions) or 5,000 (others), write 3,000 RPS, list 2,000 RPS; a target, not a hard quota. The page does not state throttling behaviour or a separate quota for PAR creation (**UNVERIFIED**: I could not find a documented rate limit for `CreatePreauthenticatedRequest`; assume it is counted as a write/management call and may be throttled with 429).
- The existing summaries route returns up to `ALBUM_COVER_IMAGES` (default 5, max 10; `config/env.ts:25-27`) covers for each of up to 100 albums per page (`albumSummaryRoute.ts:8-9`, default 50). Worst case **500 URLs per request** (100 x 5); default page **250** (50 x 5); hard ceiling in code 1,000 (100 x 10).
- No thumbnails exist today: covers are full-size originals up to `MAX_UPLOAD_BYTES` (10 MB default). ASSUMPTION for sizing: average original 3 MB, average 320 px WebP thumbnail 25 KB.
- Latency of one OCI API call from a same-region pod: ASSUMPTION 50 to 150 ms (not measured).

### 4.2 Option A: per-object PAR with short expiry, created on demand

Per `GET /albums/summaries`: 250 to 500 `CreatePreauthenticatedRequest` calls (worst 1,000). With concurrency 20: 500 x 100 ms / 20 = **about 2.5 s extra latency** (ASSUMPTION), worse with throttling; one slow call delays the page (current code drops only failed covers). Each call creates a persistent bucket resource: one user loading the home page every 5 minutes for an hour creates up to 6,000 PARs; PARs expire but **remain resources** (whether expired PARs stay listed until deleted is UNVERIFIED; the docs say they are listable/deletable), so a cleanup job and the `ListPreauthenticatedRequests` pagination become an operational concern. Cost: PAR creation itself has no documented charge (UNVERIFIED), but it uses write-class capacity and the broad `PAR_MANAGE` grant. Leak window: the TTL (minimum practical about 60 s because of clock skew); revocable only by deleting the PAR (needs its id, which we do not store). Browser loads bytes directly from OCI (no backend bandwidth). Satisfies the owner's wording literally.

### 4.3 Option C: backend-authorized streaming endpoint with a short-lived backend-signed token

Per summaries request: **0 OCI calls**; 250 to 500 local HMAC computations (microseconds each, REASONED). Bytes are read when the browser loads each `<img>`: one `GetObject` per image through the backend.

Design:
- Endpoint `GET /images/:id/content?v=thumb|full&t=<token>`. **It cannot sit behind `requireAuth`** because `<img>` cannot send `Authorization`. It is mounted before `protect` in `app.ts`, with its own IP limiter.
- Token: `t = base64url(payload) + "." + base64url(HMAC-SHA256(secret_kid, payload))`, `payload = { v:1, kid, iid: <imageId>, uid: <userId>, var: "thumb"|"full", exp: <unix seconds> }`. `node:crypto` only (no new dependency); compare with `timingSafeEqual`. TTL 60 to 300 s (default 300).
- Verification on every request: signature (try the active and the previous key), `exp`, then **owner-scoped SQL** (`image -> collection -> album.user_id = payload.uid` and `image.id = payload.iid`): one indexed query. Deleting the image, the collection, or the account therefore **revokes immediately**, which no PAR can do.
- "No reuse across users": a token is bound to `uid` and `iid` and cannot be altered (HMAC), and the backend re-checks that `uid` still owns `iid`. **It cannot stop a stolen URL being replayed by another person within its TTL**, because the browser cannot send identity with `<img>`; that is the same bearer property as a PAR (state this honestly in the contract).
- Rotation: `IMAGE_TOKEN_SECRETS=kid1:key1,kid2:key2`; sign with the first, verify with all; rotate by prepending a new key and removing the old one after one TTL. 32-byte random keys.
- Stable URLs for browser caching: if `exp` is a fresh `now + ttl` each time, every summaries call produces new URLs and the browser cache never hits. Mitigation: round `exp` up to a window boundary (for example the next 5-minute boundary plus 5 minutes), so repeated requests in a window return the **same** URL; the response then carries `Cache-Control: private, max-age=<seconds to exp>`.
- Response headers: `Content-Type` from the **DB** (validated type, never from the client), `X-Content-Type-Options: nosniff`, `Content-Disposition: inline` with a fixed name, `Cache-Control: private, max-age=<remaining>`, and **`Cross-Origin-Resource-Policy: cross-origin`**. This last point is essential: `helmet()` (`middleware/security.ts:9`) sets `Cross-Origin-Resource-Policy: same-origin` by default (VERIFIED in `node_modules/helmet`), which would make the browser block an `<img>` served by the backend origin when the page is on the frontend origin. The route must override it. The frontend's CSP `img-src` (frontend, owner/FE side) must allow the backend origin: describe to the Frontend Engineer.
- Costs: backend CPU/bandwidth. With the original images as covers, one page of 250 covers is about 750 MB through the backend (3 MB x 250); with 25 KB thumbnails about 6 MB. **Option C is only acceptable with thumbnails**, which require generating a derived object at upload (needs an image library, section 6.4). Pod memory is bounded by streaming (`getStream` piped to the response, no buffering).
- Also needs: the **general per-IP limiter must not count image requests** (250 per page against 300 per 15 minutes would lock a user out on the first page load; section 9).
- Leak window: the TTL (60 to 300 s), revoked earlier by deleting/moving the image.
- Does not use OCI URLs: it does **not** literally satisfy "short-lived OCI Object Storage access URLs".

### 4.4 Option B: PAR with caching

First load identical to A (250 to 500 creates); afterwards reuse. Where cached: per-process memory `Map<imageId, {url, expiresAt}>` (lost on restart, **not shared across replicas**, so each replica pays separately) or PostgreSQL (extra writes, stores bearer URLs at rest: not recommended). A cached PAR must be **per image, not per user** to be reusable, and it is authorized at hand-out time (the backend checks ownership before returning it), so it is safe to share only if the cache is consulted after the owner check. Lifetime: cache until `expiresAt - 30 s`; invalidation on image deletion removes the cache entry but **cannot revoke** a handed-out PAR unless its id is kept and `DeletePreauthenticatedRequest` is called (extra state and calls). Longer TTLs raise hit rate and the leak window together. Resource churn: about (images viewed per TTL window) PARs per TTL, still unbounded growth proportional to traffic. Needs `PAR_MANAGE`. Cheaper than A, still the broadest permission and an operational clean-up task.

### 4.5 Option D: hybrid

PAR only for **full-size views** (one `CreatePreauthenticatedRequest` per photo opened, per user action, TTL 300 s: about 1 call per click, negligible volume) and option C for **thumbnails and covers** (the high-volume path). Summaries: 0 OCI calls; full-size view: 1 PAR; the large bytes (full-size) go straight from OCI to the browser without passing the backend; the small bytes (thumbnails) pass the backend. Needs `PAR_MANAGE` (for the occasional PAR) and thumbnails. This is the best fit if the owner wants OCI URLs where the bytes are large.

### 4.6 Comparison (per `GET /albums/summaries`, default page 50 x 5 = 250 covers; worst 100 x 5 = 500)

| | A: PAR on demand | B: PAR + cache | C: streaming + token | D: hybrid |
|---|---|---|---|---|
| OCI API calls to build the response | 250 (500) | 250 (500) first load, ~0 within TTL on same replica | **0** | **0** |
| Extra latency on the summaries call | about 1.3 s (2.5 s) at concurrency 20 (ASSUMPTION) | same first load, then ~0 | **microseconds** | microseconds |
| OCI calls when images load | 250 direct GETs (not through backend) | same | 250 `GetObject` via the backend | 250 `GetObject` (thumbs) |
| Bytes through the backend | 0 | 0 | thumbs ~6 MB (originals ~750 MB: unacceptable) | thumbs ~6 MB; full-size 0 |
| PAR resources created per page view | 250 (500) | up to 250 (500) per TTL per replica | 0 | 0 on lists, 1 per full view |
| IAM breadth | `manage buckets` (PAR_MANAGE, incl. bucket delete) | same | **objects only** | `manage buckets` |
| Leak window | TTL (>= 60 s) | TTL | TTL | TTL |
| Revocation on delete / account removal | PAR delete only if id tracked | same | **immediate** (DB check) | immediate for thumbs; TTL for full |
| Browser cache | by PAR URL | same | needs stable `exp` windows | thumbs as C |
| Literal fit with "OCI access URLs, backend-authorized" | **Yes** | Yes | **No** (backend URL) | Partly (full-size only) |

### 4.7 Recommendation and OWNER DECISION

The owner wrote: "short-lived OCI Object Storage access URLs", authorized by the backend before generation. **Options A and B satisfy that sentence exactly, but at the cost of up to 500 API calls per page, persistent PAR resources, `manage buckets` permission and weaker revocation. Option C is technically the best match to the underlying goals (private photos, short exposure, backend authorization, least privilege, immediate revocation) but it deviates from the wording because the URL points at the backend, not at OCI.** I am not making that change silently: this is **OWNER DECISION 1** (section 15).

My recommendation: **C first, with thumbnails** (Phases 3 to 5), and keep the interface so that **D (PAR for full-size) can be added later** if backend bandwidth for full-size images becomes a problem or the owner insists on OCI URLs for large downloads. If the owner prefers A/B/D, nothing else in the plan changes except the read-URL adapter, the IAM request and the extra tests listed in 13.

### 4.8 Contract, `<img>` and expiry behaviour

- Contract stays provider-neutral: every image is `{ id, url, expiresAt }` (summaries unchanged in shape); nothing OCI-specific (no bucket, namespace, region, key, PAR id) in any response. For thumbnails vs full-size, an additive field is proposed: `{ id, url, expiresAt, thumbUrl?, thumbExpiresAt? }` or two entries; to be agreed with the Frontend Engineer (section 12.4).
- `<img>` loading needs **no CORS** (no `crossorigin` attribute, no `fetch`). If the frontend ever fetches the bytes as a blob it needs CORS on the backend (option C: add `Access-Control-Allow-Origin` per the existing allow-list) and, for PAR URLs, bucket CORS which the application cannot configure (UNVERIFIED that OCI supports it). Recommend `<img>` only, with `referrerpolicy="no-referrer"` so the app's page URL is not sent to the storage host (PAR case).
- Caching: URLs are bearer capabilities; `Cache-Control: private, no-store` on JSON responses (already set) and `private, max-age=<remaining>` on image bytes.
- Expiry mid-session: the frontend keeps `expiresAt`, refetches the list (or a single image: proposed `GET /images/:id` returning `{ id, url, expiresAt }`, owner-scoped) when `expiresAt - now < 30 s`, and on any image `onError` once, retrying with a fresh URL before showing a placeholder. This matches the existing frontend expectation in `albums-summaries-contract.md` section 8.

### 5.2 Object-key scheme (reasoned choice)

Options: (a) `images/<uuid>.<ext>`; (b) `users/<userId>/<uuid>.<ext>`; (c) `users/<userId>/collections/<collectionId>/<uuid>.<ext>` (what S-10 suggested).

Recommendation: **(a) `images/<uuidv4>.<ext>` and `images/<uuidv4>.thumb.webp`**, generated server-side with `crypto.randomUUID()`; `ext` from the **detected** type (`jpg`, `png`, `webp`, `gif`), never from the client name.
- Unguessable (122 random bits), no PII (Stack user ids can be personal identifiers and would end up in access logs and PAR paths), no collection or album names (names are user text), no user-controlled path part.
- (b)/(c) give a per-user prefix that helps prefix listing and per-user bulk delete and would allow IAM `target.object.name` conditions per prefix, but they put an identifier in every URL/log line and break when a photo moves between collections (data stays under the old prefix). Since ownership lives in PostgreSQL and deletion is driven by the outbox, the prefix buys little. IAM is bucket-scoped either way.
- Cleanup and listing use the database (the source of truth); the reconciliation job (7.4) lists `images/` and anti-joins against `Image.object_key` and `storage_deletion`.

### 5.3 Fits `migrate.ts`

The repository has no migration framework (plain `CREATE TABLE IF NOT EXISTS` functions called in order from `migrations/migrate.ts:8-17`, no version table, `main().catch(console.error)` exits 0 on failure: S-15). I will follow that approach: a new `createImageStorageColumns()` in `models/image.ts` and `createStorageDeletionOutbox()` in a new `models/storageDeletion.ts`, appended to `main()`. I will **not** introduce a migration framework without approval; I recommend (separately) making failures exit non-zero. Migrations run automatically only when `NODE_ENV=development` (`server.ts:37-41`); the owner runs them elsewhere. **Agents do not run migrations against any real database.**

### 5.4 Test strategy for the migration (mocked)

Tests: (1) a unit test that calls each `create*` function with a mocked `sql` tag and asserts every statement contains `IF NOT EXISTS`/`CREATE OR REPLACE`/a `DO` guard and **no** `DROP COLUMN`, `DROP TABLE`, `TRUNCATE` (a statement lint); (2) the existing model tests pattern (`tests/models.test.ts`) for parameter capture; (3) the owner runs the migration twice against a throwaway database (manual checklist, 13.6); optionally a local Docker Compose PostgreSQL for the QA Engineer (allowed: local only).

### 5.5 Rollback plan

Phase A (additive) is reversible by simply not using the new columns: the old application ignores them. To undo: `DROP TRIGGER image_storage_deletion`, `DROP TABLE storage_deletion`, `ALTER TABLE Image DROP COLUMN ...` are **destructive and need explicit approval** (the new columns may hold the only reference to uploaded objects after cutover). Therefore: no destructive rollback script is shipped; rollback of the application is "redeploy the previous image" and the legacy columns still point at the Cloudinary assets that were never deleted by the migration. `image_url`/`public_id` are dropped only in a final, separately approved migration, after the legacy-asset retention period decided by the owner.

### 5.6 Migrating EXISTING images

State today (VERIFIED in code): each existing row has `image_url` (Cloudinary `secure_url`) and `public_id` (`collections/<name>/<random>`), the asset is `type: "authenticated"` in Cloudinary. The number of rows and whether real photos exist is UNKNOWN (no database access).

Options:
1. **One-off copy script run by the owner** (recommended): reads rows where `object_key IS NULL`, downloads the original from Cloudinary, validates with the same pipeline as uploads, `put`s to OCI, updates the row (`object_key`, metadata, `migrated_at`) in a single statement, resumable and idempotent, `--dry-run` and `--limit`, logs counts and ids only (no URLs, no keys with names).
2. Read-through at runtime (serve legacy rows from Cloudinary until migrated): keeps `cloudinary` and its credentials in the running service, contradicting the owner's instruction. Rejected.
3. Accept loss/re-upload by users: only if the owner confirms the current data is test data.

How the script talks to Cloudinary without keeping the dependency: it lives outside the backend package (for example `backend/scripts/legacy-copy/`, not in `backend/package.json`), computes the signed delivery URL with `node:crypto` (SHA-1 signature of the transformation/public-id string + secret, the documented Cloudinary `s--sig--` scheme: UNVERIFIED here) or installs the `cloudinary` package **ad hoc in the owner's shell** (`npm i --no-save`) for the one run. Its credentials (`LEGACY_CLOUDINARY_*`) are supplied by the owner's shell, never in `.env.example`. This is the single documented exception to "no Cloudinary".

**Served in the meantime:** no runtime read-through is needed if the order is: (1) run the additive migration (old app unaffected); (2) run the copy script while the old app still serves; (3) deploy the new backend (reads only `object_key`); (4) re-run the script for rows uploaded since step 2; (5) frontend cutover. Between 3 and 5 legacy rows that still lack `object_key` are **omitted from covers and listed with `url: null`** (proposed explicit state), never served through a permanent Cloudinary URL.

## 6. Upload pipeline

### 6.1 Flow and where the bytes live

```
authn -> per-user limiter -> multer (limits) -> owner check of collection -> for each file:
   validate (magic bytes, declared vs detected, dimensions) -> [decode/re-encode, strip EXIF, thumbnail]
   -> key = images/<uuid>.<ext> -> storage.put(If-None-Match:*) -> INSERT Image -> cleanup temp
```

Options for the bytes: (i) **disk temp (current, `dest: "uploads/"`)**: bounded memory, works with large files, but a writable local disk in the container is needed (the owner must provide a writable `emptyDir` or similar: REQUIREMENT), and temp files must be removed on every path (already implemented and tested, S-04); (ii) **memory (`multer.memoryStorage`)**: simplest and removes the disk requirement; with `fileSize` 10 MB and `files` 10 a single request holds up to 100 MB, times concurrent requests: needs a lower `files`/`fileSize` or a concurrency cap; (iii) pure streaming to OCI: cannot validate content before storing, rejected.
Recommendation: **keep disk temp** (no behaviour change, validated code), set `files` to 10 as today and process files sequentially so at most one decoded image is in memory.

### 6.2 Multer limits (S-21), proposed values

| Limit | Value | Reason |
|---|---|---|
| `fileSize` | `UPLOAD_MAX_BYTES`, default **10 MiB** (unchanged) | Existing contract; typical phone JPEG 2 to 6 MB; PUT limit at OCI is 50 GiB so not a constraint |
| `files` | **10** (unchanged) | Existing contract and UI |
| `parts` | **11** (10 files + 1 slack) | Bounds total parts; today unbounded (S-21) |
| `fields` | **0** | The upload form sends only files; any text field is rejected (`LIMIT_FIELD_COUNT`) |
| `fieldSize` | 1 KiB | Irrelevant with `fields: 0`, set defensively |
| `fieldNameSize` | 32 bytes | Field name is `images` |
| `headerPairs` | 20 | Default is 2000; bounds multipart part headers |
| Allowed field name | exactly `images` (already enforced by `upload.array("images", 10)`) | |
| Aggregate request size | Reject early via `Content-Length` > `files x fileSize + 64 KiB` before multer runs | Today there is no total cap; multer has none |

Add tests for each (many text parts -> 400, oversize header count, wrong field).

### 6.3 Content validation

1. **Magic bytes**: extend `lib/imageSignature.ts` (currently 12 bytes, JPEG/PNG/GIF/WebP; `SIGNATURE_BYTES = 12` at line 6) and **compare with the declared MIME**; reject mismatch (S-24a). Store the **detected** type.
2. **Extension allowlist**: client filename extension must be in `jpg|jpeg|png|webp|gif` (informational; the stored extension comes from the detected type).
3. **SVG and other active formats** are rejected (already the case: not in the allowlist and no signature).
4. **Dimension and decompression-bomb limits**: a 10 MB PNG can decode to gigapixels. Proposed: max **8,000 px per side**, **40 megapixels** total, reading dimensions from the header before decoding (needs a header parser or an image library). Without a library this check is **not** possible beyond partial manual parsing; a hand-written parser is itself a risk.
5. **Polyglots** (valid image header plus appended script/archive): only a **full decode and re-encode** removes them (S-24b). Header checks alone cannot.

### 6.5 EXIF/GPS privacy

Phone photos usually carry GPS position, device model and timestamps in EXIF. Options: (1) store originals untouched (preserves metadata the owner may want, but exposes location to anyone who gets the URL and to the app at no benefit); (2) **strip on re-encode** via sharp (recommended; orientation applied before stripping so images do not rotate); (3) strip but keep a sanitised copy of selected fields (date taken) in columns (adds a feature). Recommendation: (2) now, (3) only on request. This is part of OWNER DECISION 3 because re-encoding changes the stored bytes (not bit-identical to what the user uploaded), which the owner may consider a product change.

### 6.6 Failure handling and idempotency

- **Object stored, DB insert fails** (or the process dies in between): compensating `storage.delete(key)` in the error path; if that fails or the process crashes, the object is an **orphan** with no row. Mitigation: the reconciliation job (7.4) deletes bucket objects under `images/` older than 1 hour that have no `Image` row.
- **DB row exists, object missing** (never happens in the normal order since the row is written after `put`; can happen after a bucket-side deletion): `getStream` 404 -> 404 to the client and an error log of the image id; summaries covers dropped (already the pattern, `albumSummaryRoute.ts:76-82`).
- Per-file result instead of all-or-nothing (S-24c): upload returns `201` with `images[]` for the files stored and `failed[]` (index and generic reason) so a partial failure does not hide stored files; or `207`-style. Contract detail: agreed with the Frontend Engineer.
- **Idempotency**: key is generated server-side per file; `put` uses `If-None-Match: *`; retries of the same HTTP request create new keys (a client retry creates duplicates). Optional: an `Idempotency-Key` header persisted in a small table (proposed only if the frontend retries uploads; not recommended now).
- Object headers set at `put`: `Content-Type` (detected), `Content-Disposition: inline` (no filename; the original name is only in the DB), `Cache-Control: private, max-age=31536000, immutable` is acceptable for PAR/direct delivery of immutable keys but for option C the backend sets its own response headers, so the object-level value is `private, no-store`-equivalent `private, max-age=0` (decision follows the URL option). No public ACL exists in OCI at object level; privacy is the bucket's private access type (owner's setting, smoke test item 3). `opcMeta` carries nothing personal.
- Logging: object keys and image ids may be logged at debug level; **never** URLs, tokens or original filenames.

## 7. Deletion and cleanup (S-09)

### 7.1 What "deleted" means

A row removed from `Image` is the authoritative deletion. The storage object follows via the outbox. Outstanding temporary URLs: option C: **dead immediately** (the DB check fails); PAR options: valid until their `timeExpires` unless the PAR id was kept and `DeletePreauthenticatedRequest` is called (needs `PAR_MANAGE`); with TTL 300 s the residual window is at most 5 minutes (document it).

### 7.2 Ordering: database first, storage second, via a transactional outbox

1. In one statement/transaction, `DELETE FROM Image` (directly, or by cascade from collection/album/account). The `BEFORE DELETE` row trigger (5.1) inserts the keys into `storage_deletion` **in the same transaction**: either both happen or neither. No window where the row is gone and the key is forgotten.
2. A drainer (in-process loop started in `server.ts`, interval 30 s, batch 50, `SELECT ... FOR UPDATE SKIP LOCKED` so several replicas can run it) calls `storage.delete(key)`; success or "not found" -> delete the outbox row; failure -> `attempts+1`, exponential `next_attempt` (1 min up to 1 h), `last_error` = error code; alert at `attempts >= 10` (log).
3. `DELETE /images/:id` additionally tries the storage delete **inline, best effort** after the DB commit, so the common case is immediate; on failure the outbox retries.
Storage first, DB second (current order, `imageRoute.ts:144` then `:161`) is rejected: a failure between them leaves a row pointing at a missing object.

### 7.3 Cascades

Because the trigger is on `Image`, every path is covered with no route changes: `DELETE /collections/:id` (`collectionRoute.ts:126-136`), `DELETE /albums/:id` (`albumRoute.ts`), and **account deletion** (cascade from `neon_auth.users_sync`, which the application never executes itself). Caveats: Neon's HTTP driver (`config/db.ts`: `neon()` over `@neondatabase/serverless`) is stateless, so the outbox logic must stay inside single SQL statements (it does); a bulk delete of very many images produces many outbox rows (fine).

### 7.4 Reconciliation (proposal)

A script/endpoint run on demand or by the in-process loop at low frequency: list `images/` (OBJECT_INSPECT), and for objects older than 1 hour with no `Image.object_key`/`thumb_key` match, enqueue them to `storage_deletion`. Never deletes recent objects (in-flight uploads). Dry-run mode prints counts. Needs the list permission (3.4).

### 7.5 Bucket-side

Versioning or retention (owner's bucket decision) changes what `DeleteObject` means; ask (3.4 item 5).

## 8. Authorization and ownership: F5 exact change

### 8.1 Current code (VERIFIED)

`backend/models/image.ts:61-63`:
```ts
export async function deleteImage(id: string) {
  await sql`DELETE FROM Image WHERE id = ${id};`;
```
Caller `backend/routes/imageRoute.ts:133-161`: `getImageById(id, currentUserId(req))` at `:138` (owner-scoped SELECT, `models/image.ts:49-55`) returns 404 if not owned; then Cloudinary calls; then `deleteImage(id)` at `:161`. The ownership check and the delete are two separate statements: not exploitable today (the route checks first), but any future caller of `deleteImage(id)` skips ownership, and there is a check-then-act gap.

### 8.2 Proposed SQL (single owner-scoped statement, same style as `deleteCollection`, `models/collection.ts:55-61`)

```ts
/** Deletes the image only if its album belongs to userId. Returns the removed keys, or null when nothing matched. */
export async function deleteImage(id: string, userId: string) {
  const rows = await sql`
    DELETE FROM Image
    WHERE id = ${id}
      AND collection_id IN (
        SELECT c.id FROM Collection c JOIN Album a ON a.id = c.album_id WHERE a.user_id = ${userId}
      )
    RETURNING id, object_key, thumb_key;
  `;
  return rows[0] ?? null;
}
```
The outbox trigger records the keys inside the same transaction. The route becomes: validate `isUuid`, call `deleteImage(id, userId)`; `null` -> 404 `{ "error": "Image not found" }`; else best-effort inline `storage.delete`, then 200. It no longer needs a prior `getImageById`.

### 8.3 Rationale

Authorization is enforced **in the statement that mutates**, not only before it; one round trip fewer; identical 404 for missing and foreign ids (no existence leak); removes the signature that allows an unscoped delete.

### 8.4 Tests for approval (A = Alice owns the image, B = Bob)

1. A deletes own image -> 200; `deleteImage` called with `(id, ALICE)`; storage `delete` called once with the image's key; outbox covers the failure case.
2. **B deletes A's image -> 404, image still present, storage `delete` NOT called.**
3. Unauthenticated -> 401, nothing called.
4. Unknown UUID -> 404; malformed id -> 404 without touching the model (existing pattern).
5. Model-level (parameter-capture test, as `tests/models.test.ts`): the SQL contains the owner subquery and binds `id` and `userId` as parameters.

## 9. Per-user rate limiter (approved in principle)

### 9.1 Current state (VERIFIED)

`middleware/security.ts`: `generalLimiter` per IP 300/15 min (`:26-28`), `authFailureLimiter` per IP counts only 401, 20/15 min (`:31-40`), `uploadLimiter` and `writeLimiter` keyed by `req.auth?.userId ?? "anonymous"` (`:42-65`); settings `config/env.ts:61-66`. All use express-rate-limit 8.7.4 default in-memory store. Two hazards: if a per-user limiter were ever mounted before auth, every request would share the `"anonymous"` bucket; and `/albums/summaries` has no per-user limiter although it is the most expensive read (S-20).

### 9.2 Design

- Order per request: `generalLimiter` (IP, coarse backstop) -> `authFailureLimiter` (IP, counts 401 only) -> `requireAuth` -> **per-user limiter for the route class** -> handler. The per-user limiters **require** `req.auth`: build them with a key function that **throws** (or returns 500) if `req.auth` is missing, never `"anonymous"`.
- Unauthenticated routes (`/` liveness, and the token-protected `/images/:id/content`): keyed by **IP** (and, for content, additionally by the verified token's `uid` after the HMAC check, before any database access). Failed-auth traffic: the existing 401 counter by IP. The general IP limiter must **skip** `/images/:id/content`, otherwise one page of 250 covers exhausts 300 requests per 15 minutes.
- Window 15 minutes (consistent with the existing config), all values env-overridable.

| Route class | Key | Limit per 15 min (proposal) | Reasoning |
|---|---|---|---|
| `GET /albums/summaries` | user | **120** | Heavy query, one call per page view plus refresh near expiry; 8 per minute is generous for a human |
| Other reads (`GET /albums`, `/collections*`, `GET /images/collection/:id`, `GET /images/:id`, `GET /me/consent`) | user | **600** | Existing UI makes several calls per page |
| Image content `GET /images/:id/content` | IP before token, then user after token | **IP 6,000, user 3,000** | 250 to 500 thumbnails per page view; about 6 to 12 full page views per window; stable URLs + browser cache reduce repeats |
| Upload | user | **30 requests** (existing) and a **file budget of 300 files** | Existing request cap; per-request count is 1..10 files (S-21 note: the limiter counts requests, not files) |
| Writes (`POST/PUT/DELETE` on albums, collections, images) | user | **60** (existing) | Unchanged |
| Consent `POST` | user | 20 | Rare action, low limit |
| General IP backstop | IP | raise from 300 to **1,500** once the per-user limiters exist and the proxy IP is correct (section 10) | 300 per IP penalises households/offices behind one NAT; per-user limits now carry the load. Owner decision |

### 9.3 Store

In-process memory (the express-rate-limit default). With **N replicas** behind a load balancer, each keeps its own counters: the effective limit is up to N times higher (and a restart resets it); sticky routing would make it exact, which we cannot assume. Acceptable for abuse mitigation, not for hard quotas. A shared store (Redis, or PostgreSQL counters) would make limits exact but is **new infrastructure/dependency: not proposed without approval** (OWNER DECISION 6 asks).

### 9.4 Interaction with the proxy question

Per-user limiters do **not** depend on the client IP (they use the verified user id), which is why they are preferred; the IP-based layers (general, auth failure, content-before-token) are only meaningful once `trust proxy` matches the real topology (section 10). Until then behind a proxy with `0` hops all users share one IP bucket (S-01).

## 10. Trusted proxy topology (S-01): no value is chosen here

### 10.1 How Express `trust proxy` works (Express 5.1, `proxy-addr@2.0.7`, VERIFIED `npm ls`)

`req.ip` is derived from the socket address plus the `X-Forwarded-For` (XFF) list, trusting only the configured hops: a **number** `n` trusts the `n` nearest hops (the client address is taken `n` entries from the right of the chain); a **subnet/CIDR list** trusts any hop whose address falls in the list and takes the first untrusted address from the right; `false` ignores XFF entirely (`req.ip` is the socket peer). The app currently sets only a number, and only when `> 0` (`app.ts:34`, `config/env.ts:56`).

### 10.2 Realistic topologies

| Topology | Hops the app sees | XFF as built |
|---|---|---|
| Local development, browser -> backend directly (Vite on `127.0.0.1:8080` and API on `:5000`, with CORS; the Vite dev server does not proxy API calls here) | 0 | none; `req.ip` = browser |
| Local Docker Compose with a reverse proxy container | 1 | proxy appends client address |
| OKE: browser -> **OCI Load Balancer** -> Service/pod (no ingress controller) | 1 (the LB) | the LB appends the connecting address to XFF (behaviour per OCI LB docs: not re-verified in this session) |
| OKE: browser -> OCI LB -> **ingress controller** (for example NGINX) -> pod | 2 | LB appends client; the ingress appends the LB address, unless configured to overwrite/ignore incoming XFF |
| Any of the above with a CDN/WAF in front | +1 | the CDN also appends |
| OCI **network** load balancer (layer 4) | 0 or ingress only | may preserve the source IP and add no XFF; then the ingress is the only hop |

### 10.3 Risk of wrong values

- **Too low (0 behind a proxy):** `req.ip` is the proxy; all users share the per-IP limiters; the auth-failure limiter lets **one client lock everyone out** after 20 bad tokens (S-01).
- **Too high:** the app trusts addresses supplied by the client in XFF: a client sets any `X-Forwarded-For` and chooses its own "IP", **evading** per-IP limits and poisoning logs.
- **CIDR list instead of a count:** robust to changing hop counts but the installed `proxy-addr@2.0.7` is affected by advisory **GHSA-jqcg-44mw-7w3h** (critical, spoofing via an IPv4-mapped IPv6 address against a trusted subnet; fixed in 2.0.8; Express 5.1.0 allows `^2.0.7`). A CIDR configuration should come with the targeted update `npm update proxy-addr` (same kind of change as section 11; not run).

### 10.4 What the application should do (proposal)

Read `TRUST_PROXY_HOPS` (integer) or `TRUST_PROXY_CIDRS` (comma list); treat **unset** differently from explicit `0`. In production (`NODE_ENV=production`) with neither set: log a warning at startup (the M4 warning) and optionally refuse to start with `REQUIRE_TRUST_PROXY=true` (OWNER DECISION 5 on warn versus refuse). Reject invalid or negative values at startup. Never default to a non-zero guess. Add a startup log line (not the headers) stating the mode. Express `trust proxy` stays off for `0`.

### 10.5 Questions for the infrastructure owner (precise list)

1. Which components sit between the internet and the backend pod, in order (CDN/WAF, OCI load balancer type: flexible vs network, ingress controller product and version)? 
2. For each hop: does it **append** to `X-Forwarded-For`, **overwrite** it, or pass it through? (ingress controllers differ by configuration, for example whether forwarded headers from outside are trusted.)
3. Does the OCI load balancer preserve the client source IP, and is `externalTrafficPolicy` set so the pod sees the ingress, not a node address?
4. Is the number of hops identical for **every** public path to the backend (for example a direct node port or a second ingress for an admin path)?
5. Will it change (adding a CDN, replacing the ingress)? If yes, prefer the CIDR list of the LB/ingress subnets and tell us the ranges.
6. Is the backend reachable by any path that bypasses the proxies (pod IP, internal service from other namespaces)? Those callers could send arbitrary XFF.
7. Which source address does the pod see for health checks and for in-cluster calls?
